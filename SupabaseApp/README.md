# Веб-сервис заявок на автоматизацию

**Приложение:** https://ips-analytics.github.io/automation-test-task/ · **Код:** эта папка

Сотрудник регистрируется, создаёт заявку (название, описание, категория), следит за её статусом, ищет и фильтрует свои заявки. Авторизация и данные — Supabase. Каждый пользователь видит и меняет только свои заявки, и это ограничение действует в базе данных, а не только в интерфейсе.

## Требования и как они выполнены

| Требование | Реализация |
|---|---|
| Регистрация, вход и выход по email и паролю | Supabase Auth: `signUp`, `signInWithPassword`, `signOut`; ошибки переведены в понятный текст |
| Название, описание и категория обязательны | проверка в форме с подсветкой полей + `NOT NULL` и `CHECK` в таблице |
| Новая заявка получает статус «Новая» | значение по умолчанию в базе; передать другой статус при создании клиент не может — нет права на колонку |
| В списке — название, категория, дата создания, статус | карточки, новые сверху |
| Открыть и отредактировать свою заявку, сменить статус | страница заявки с переключателем «Новая / В работе / Завершена» |
| Поиск по названию и фильтр по статусу | мгновенно на клиенте, счётчик «Найдено N из M», кнопка сброса |
| Данные остаются после обновления страницы и повторного входа | всё хранится в Postgres; сессия — в localStorage; открытая заявка — в адресе (`#/requests/<id>`) |
| Чужие заявки недоступны, в том числе при прямом обращении | RLS-политики и права на колонки; проверено скриптом через API |
| Удобно на компьютере и телефоне | адаптивная вёрстка; поля 16 px (iOS не увеличивает страницу), кнопки от 44 px |
| Виден результат сохранения, при ошибке — понятное сообщение | уведомления «Заявка создана» и «Изменения сохранены»; ошибки у поля и над кнопкой, введённое не теряется |
| Повторное нажатие не создаёт дубль | три уровня: синхронный флаг до перерисовки, блокировка формы на время запроса, id заявки генерируется на клиенте один раз — повторная отправка не создаёт дубль, а дописывает актуальные поля в уже созданную заявку |

## Стек и структура

React 19, TypeScript, Vite, `@supabase/supabase-js`. Без UI-библиотек и роутера: маршруты на hash, поэтому статический хостинг (GitHub Pages) не требует настройки.

```text
src/
  App.tsx                    сессия, шапка, выбор экрана
  components/AuthScreen.tsx  вход и регистрация
  components/RequestsList.tsx список, поиск, фильтр
  components/RequestForm.tsx создание и редактирование
  components/Toasts.tsx      уведомления
  lib/supabase.ts            клиент, типы, подписи категорий и статусов
  lib/errors.ts              ошибки Supabase → понятный текст
  lib/router.ts              hash-маршруты
supabase/migrations/…sql     таблица, RLS, права
scripts/rls-check.mjs        проверка изоляции через API
```

## Настройка Supabase

1. Создать проект на [supabase.com](https://supabase.com) (бесплатного плана достаточно).
2. **SQL Editor** → выполнить [`supabase/migrations/20261103120000_requests.sql`](supabase/migrations/20261103120000_requests.sql). Будут созданы таблица, ограничения, триггер `updated_at`, RLS-политики и права.
3. **Authentication → Sign In / Providers → Email:** провайдер включён. Для демонстрации выключить **Confirm email** — тогда регистрация сразу открывает сессию. Если подтверждение оставить, приложение покажет «Письмо отправлено…», но встроенная почта Supabase отправляет лишь несколько писем в час — для реальной работы нужен свой SMTP.
4. **Authentication → URL Configuration:** Site URL и Redirect URLs — адрес приложения (`https://ips-analytics.github.io/automation-test-task/`). Нужно для ссылок из писем.
5. **Project Settings → API Keys:** скопировать Project URL и publishable key (подойдёт и legacy anon key). Это публичные значения, доступ к данным ограничивают RLS-политики. Секретный ключ приложению не нужен.

### Схема данных

| Колонка | Тип | Правило |
|---|---|---|
| `id` | `uuid`, PK | генерирует клиент (ключ идемпотентности) или база |
| `user_id` | `uuid` → `auth.users` | по умолчанию `auth.uid()`, клиент задать или изменить не может |
| `title` | `text` | 1–200 символов, не только пробелы |
| `description` | `text` | 1–5000 символов, не только пробелы |
| `category` | `text` | `bot`, `integration`, `report`, `other` |
| `status` | `text` | `new`, `in_progress`, `done`; по умолчанию `new` |
| `created_at`, `updated_at` | `timestamptz` | ставит база, `updated_at` — триггером |

**Доступ:**

- `SELECT`, `UPDATE`, `INSERT` — только строки, где `auth.uid() = user_id`;
- `DELETE` — политики нет, удаление запрещено (в интерфейсе его тоже нет);
- у роли `anon` прав нет; у `authenticated` — чтение, вставка только колонок `id, title, description, category`, изменение только `title, description, category, status`. Поэтому нельзя создать заявку от чужого имени, сразу в другом статусе или подменить дату.

## Запуск

Нужен Node.js 22.12 или новее.

```bash
cd SupabaseApp
npm install
cp .env.example .env.local
npm run dev
```

В `.env.local` — Project URL и publishable key из шага 5.

Полностью локально, без облака (нужен Docker): `npx supabase start` применит миграцию и выведет URL и ключ для `.env.local`. Для экономии можно не поднимать лишние сервисы:

```bash
npx supabase start -x realtime,storage-api,imgproxy,studio,edge-runtime,logflare,vector,supavisor,postgres-meta,mailpit
```

## Деплой

[`.github/workflows/ci.yml`](../.github/workflows/ci.yml) на push в `main` и на каждый PR запускает сборку приложения (`tsc` + `vite build`), а из `main` публикует сборку на GitHub Pages. Права на публикацию есть только у job’а деплоя. В репозитории нужны:

- Settings → Secrets and variables → Actions → **Variables:** `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`;
- Settings → Pages → Source: **GitHub Actions**.

## Проверка изоляции данных

`npm run rls-check` входит под двумя пользователями через публичный API — так же, как мог бы сделать человек с ключом из браузера, — и проверяет сценарии в обход интерфейса. Пользователей лучше передать через `RLS_A_EMAIL`, `RLS_A_PASSWORD`, `RLS_B_EMAIL`, `RLS_B_PASSWORD`. Без них скрипт создаёт двух новых — это работает только при выключенном подтверждении email, поэтому удобнее запускать его на локальном Supabase. Тестовые заявки и пользователи остаются в базе: удаление запрещено намеренно.

```text
✓ A создаёт заявку: статус «Новая», автор — A
✓ Нельзя создать заявку сразу в другом статусе
✓ База отклоняет название из одних пробелов и длиннее 200 символов
✓ Нельзя создать заявку от имени другого пользователя
✓ B не видит заявку A в своём списке
✓ B не может прочитать заявку A по id
✓ B не может изменить заявку A
✓ B не может удалить заявку A
✓ Без входа заявки недоступны
✓ A меняет статус своей заявки
✓ A не может передать заявку другому пользователю
✓ A не может подменить дату создания
✓ Заявка A не изменилась от действий B

Все проверки пройдены.
```

## Как проверено

На локальном Supabase в Docker (та же миграция, что для облака):

- `npm run build` — проверка типов TypeScript и сборка проходят;
- `npm run rls-check` — 13 из 13;
- повторная отправка с тем же id (ответ на первую потерялся) обновляет заявку, а не создаёт дубль — проверено отдельным скриптом;
- ручной прогон в браузере: ошибки входа («Проверьте адрес…», «Неверный email или пароль»); регистрация; пустая форма → ошибки у всех трёх полей и фокус на первом; тройной клик по «Создать заявку» → одна заявка; редактирование и смена статуса; поиск, фильтр, пустой результат и сброс; обновление страницы; выход и повторный вход; второй пользователь видит пустой список, а прямая ссылка на чужую заявку отвечает «Заявка не найдена или у вас нет к ней доступа»; ширина 375 px без горизонтальной прокрутки; остановленный backend → «Нет связи с сервером…», форма разблокирована, повтор после восстановления сохраняет изменения; в консоли нет предупреждений React.

Облачный проект Supabase и GitHub Pages проверяются при публикации — по сценарию ниже.

## Сценарий демонстрации

1. Регистрация → выход → вход.
2. «Новая заявка»: нажать «Создать» с пустыми полями — ошибки у полей; заполнить — «Заявка создана», в списке статус «Новая».
3. Открыть заявку, изменить описание и статус — «Изменения сохранены», в списке новый статус.
4. Поиск по слову из названия, фильтр по статусу, «Сбросить фильтры».
5. Обновить страницу — данные и вход на месте; выйти и войти — данные на месте.
6. Второй пользователь в окне инкогнито: пустой список; ссылка на заявку первого — «не найдена». То же через API — `npm run rls-check`.
7. DevTools → режим устройства 375 px.

## Использование AI

Инструмент — AI-агент для программирования в терминале: он пишет код и сам запускает проверки. С его помощью написаны SQL-миграция, приложение, скрипт проверки RLS, workflow для n8n и документация.

**Получилось сразу:** схема с RLS и правами на колонки, компоненты и обработка ошибок. Сборка и проверка RLS прошли с первого запуска, ручной прогон дефектов в коде приложения не выявил.

**Какие проблемы возникли и как решены:**

- *Ревью перед коммитом.* Два агента-ревьюера (код и безопасность) blocker- и critical-находок не нашли, но до публикации исправлено: CHECK в базе считал длину по обрезанной строке и пропускал названия из одних пробелов; права на публикацию в CI были у всех job’ов; повтор после потерянного ответа показывал «Заявка создана», но терял последние правки; скрипт проверки RLS маскировал ошибку входа.
- *Скриншоты браузера.* Инструмент проверки однажды вернул устаревший кадр, который расходился с данными. Выводы делались по состоянию DOM, скриншоты — только для вёрстки.

**Как проверялся результат:** коду AI не доверял на слово. Изоляцию данных проверяет скрипт через API под двумя пользователями; интерфейс прогнан по всем пунктам демонстрации на локальном Supabase, включая узкий экран и отказ backend; workflow бота выполнен в настоящем n8n с моком Telegram.

## Известные ограничения

- Нет восстановления пароля и удаления заявок — в задании их нет.
- Регистрация открыта всем, а для демо выключено подтверждение email. Для реального внутреннего сервиса: включить подтверждение и свой SMTP, ограничить регистрацию корпоративным доменом (Auth Hook `before_user_created`) или приглашениями, добавить captcha и пароль от 10 символов.
- Поиск и фильтр работают на клиенте, все заявки пользователя загружаются разом (не больше 1000 — лимит `max_rows` в Supabase). Для сотен заявок на человека этого достаточно; дальше — серверный `ilike` и пагинация.
- Изменения из другой вкладки появятся после обновления страницы (без realtime-подписки); при одновременном редактировании одной заявки побеждает последнее сохранение — проверки версии по `updated_at` нет.
- E2E-тестов в репозитории нет: интерфейс проверен вручную, доступ к данным — скриптом `rls-check`.
